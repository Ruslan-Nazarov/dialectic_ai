# Задание: два диалектических движка (лёгкий и тяжёлый) для MVP «Рейтинг качества бизнес-задач»

Ты — ведущий агент (лид/интегратор) команды агентов. Нужно написать **с нуля** два
взаимозаменяемых AI-движка и стенд их сравнения. Веб-приложение («база»: карточки, рейтинг,
каталог, отклики, выбор команд, UI) пишет человек отдельно; движки подключаются к ней через
общий контракт из §2. Прочитай документ целиком до первого действия.

**Правило происхождения кода:** весь код пишется с нуля в этом проекте. Никакой ранее созданный
код (включая любые существующие диалектические фреймворки, их файлы, тесты и промпты) не
копируется и не импортируется. Разрешены стандартные открытые библиотеки (Pydantic, httpx,
FastAPI, pytest, python-dotenv и т.п.). Этот документ — спецификация, а не исходник.

## 0. Задача движка в продукте

Бизнес вводит слабое описание задачи (черновик). Движок:
1. находит, чего не хватает студенческой команде, и внутренние противоречия черновика;
2. задаёт бизнесу **≥3 уточняющих вопроса** (каждый — из конкретного противоречия/пробела);
3. по ответам собирает **карточку задачи**, где каждое поле подтверждено цитатой из слов бизнеса;
4. отдаёт базе карточку и граф рассуждения; дальше человек редактирует и подтверждает поля,
   а рейтинг считает база (не движок).

Поля карточки (фиксированные ключи): `title`, `context`, `need`, `users`, `data`,
`constraints`, `expected_result`, `success_criteria`, `contact`, `interaction_format`.

Жёсткие правила кейса, которые обеспечивает движок:
- **Не добавлять фактов**, которых бизнес не сообщал. Нет сведений → поле `null`.
- Движок ничего не публикует и не подтверждает сам: результат — черновик карточки для человека.
- Движок не оценивает команды, не выбирает исполнителей, не использует персональные признаки.
- Если провайдер LLM недоступен — честная ошибка с сохранённым прогрессом; база переключается
  на свою заглушку.
- Нужно уметь показать: промпты, формат входа/выхода и что происходит с некорректным ответом
  модели (эндпоинт `contract`, §2.3).

## 1. Диалектическая модель предметной области (общая для обоих движков)

| Понятие | В этом кейсе |
|---|---|
| Простейший процесс | потребность, как её сформулировал бизнес в черновике |
| Развитие простейшего | конкретизация: что происходит сейчас, что должно измениться, кто пользователи, какие есть материалы, сроки, как бизнес поймёт успех — **только то, что следует из черновика** |
| Противоположность | студенческая команда, начинающая работу, **зная только карточку**. Её потребность — «начать работу без вопросов к бизнесу», это другая потребность, чем «описать задачу», и она развивается независимо от того, что у бизнеса в голове |
| Развитие противоположности | что команде нужно знать, чтобы начать: входные данные, доступы, критерий приёмки, границы, контакт, формат работы |
| Противоречие | единство и несовместимость двух развитий: `gap` — бизнес считает очевидным то, чего команда знать не может; `conflict` — черновик противоречит сам себе («нужна ML-модель» + «данных нет», «к следующему месяцу» + объём на семестр, «чтобы было удобнее» без измеримого критерия) |
| Скачок | план вопросов: каждый вопрос разрешает конкретное противоречие, один факт на вопрос |
| Практика | вопросы бизнесу; **ответ человека — наблюдение**. Затем фиксация карточки, проверяемая кодом |
| Оценка практики | по каждому противоречию: ответ его разрешил / не разрешил / вскрыл новое |
| Завершение | карточка, каждое непустое поле которой опирается на цитату из черновика или ответов |

Противоположность — **не** «проверка карточки», не «альтернативная формулировка», не
отрицание черновика: у неё своя потребность. Она **задана доменом заранее**: движки не просят
модель её выбрать и не дают судье её переоценивать (см. §5.0) — модель только развивает её.

## 2. Контракт подключения к базе (общий, заморожен лидом в шаге 0)

Движки живут в пакете `engines/` и доступны базе двумя способами: in-process Python API и
тонкий HTTP-сервис (для базы на любом стеке). Выбор движка — конфигурацией
`ENGINE=light|heavy`.

### 2.1 Типы (Pydantic, `engines/common/contracts.py`)

```python
FieldName = Literal["title","context","need","users","data","constraints",
                    "expected_result","success_criteria","contact","interaction_format"]

class StartRequest(BaseModel):
    task_id: str
    draft: str                       # текст черновика
    industry: str | None = None
    field_weights: dict[FieldName, int]   # веса рейтинга из базы -> «+N баллов» у вопросов
    language: Literal["ru"] = "ru"

class Question(BaseModel):
    question_id: str                 # Q1, Q2 ...
    text: str                        # один факт, <= 200 символов, по-русски
    field: FieldName
    contradiction_id: str            # из графа
    why: str                         # какое противоречие/пробел закрывает, 1 фраза
    points_at_stake: int             # = field_weights[field], считает код, не модель

class Answer(BaseModel):
    question_id: str
    text: str                        # пустая строка = «не знаю» (валидно)

class Source(BaseModel):
    source_id: str                   # "draft" или answer_id (A1, A2 ...)
    quote: str                       # точная подстрока источника

class CardField(BaseModel):
    value: str | None
    sources: list[Source] = []       # пусто только если value is None

class CardDraft(BaseModel):
    fields: dict[FieldName, CardField]

class GraphNode(BaseModel):
    id: str
    kind: Literal["simplest","opposite","element","contradiction","question","answer","field"]
    label: str
    status: Literal["open","resolved","reopened","rejected","ok"] | None = None
    side: Literal["simplest","opposite"] | None = None

class GraphEdge(BaseModel):
    source: str; target: str
    kind: Literal["develops","contradicts","resolves","asks","answers","grounds"]

class GraphView(BaseModel):
    nodes: list[GraphNode]; edges: list[GraphEdge]

RunStatus = Literal["analyzing","waiting_answers","building_card","card_ready","failed","cancelled"]

class RunView(BaseModel):
    run_id: str; task_id: str; engine: Literal["light","heavy"]
    status: RunStatus
    pending_questions: list[Question] = []
    card: CardDraft | None = None
    graph: GraphView
    error: str | None = None          # человекочитаемо; при failed
    stop_reason: str | None = None    # machine: provider_unavailable|budget|deadline|provenance_failed|...
    metrics: dict                     # llm_calls, tokens_by_role, elapsed_s, rejections, rounds
```

`GraphView` — **единый формат для UI базы**: оба движка переводят свой внутренний граф в него.
База рисует граф по нему одинаково для обоих движков.

### 2.2 Python API (`engines/__init__.py`)

```python
class Engine(Protocol):
    name: Literal["light","heavy"]
    async def start(self, req: StartRequest) -> str            # run_id; прогон идёт в фоне
    def view(self, run_id: str) -> RunView                      # мгновенно, без LLM
    async def submit_answers(self, run_id: str, answers: list[Answer]) -> None
    async def cancel(self, run_id: str) -> None

def get_engine(name: str | None = None) -> Engine               # по ENGINE из окружения
```

Семантика: `start` создаёт независимый прогон (`asyncio.create_task`), статус сразу
`analyzing`. Когда движку нужны ответы — статус `waiting_answers`, вопросы в
`pending_questions`. `submit_answers` будит прогон. Итог — `card_ready` с `card`, либо `failed`
с `stop_reason`. Параллельные прогоны разных задач не мешают друг другу.

### 2.3 HTTP-сервис (`engines/service.py`, FastAPI)

```
POST   /engine/runs                  StartRequest            -> {run_id}
GET    /engine/runs/{run_id}                                 -> RunView
POST   /engine/runs/{run_id}/answers {answers:[Answer]}       -> RunView
DELETE /engine/runs/{run_id}
GET    /engine/runs/{run_id}/trace                           -> JSONL трассы
GET    /engine/contract?engine=light|heavy                   -> промпты, JSON-схемы ответов модели,
                                                                пример битого ответа из реальной трассы
                                                                и как он был обработан
GET    /engine/health                                        -> провайдеры: доступны/нет
```

База поллит `GET /engine/runs/{id}` раз в 1–2 с. Ошибки — 4xx/5xx с `detail`.

### 2.4 Replay

`ENGINE_REPLAY=path/to/trace.jsonl` — движок проигрывает записанный прогон с реальными
задержками между событиями (граф растёт по записи, вопросы появляются, ответы берутся из
трассы или от человека). Нужен для демо при сбое сети.

## 3. Общий слой (`engines/common/`) — пишется первым

- **LLM-клиенты:** `LLMClient.generate(messages, *, json_schema=None, max_tokens, timeout) -> LLMResult(text, usage)`.
  Реализации: GigaChat (HTTP, OAuth-токен с кэшем до истечения, TLS через CA-бандл из
  `GIGACHAT_CA_BUNDLE`, верификацию не отключать), OpenAI-совместимый (для Cerebras/Groq/др.),
  `FallbackLLM([...])`, `ScriptedLLM(responses)` для тестов. Ретраи с бэкоффом на 429/5xx/сеть
  (≤2). Пустой ответ = ошибка провайдера, не содержимое. Ключи только из `.env`;
  в репозиторий — `.env.example`.
- **Роли моделей:** `actor` и `judge` конфигурируются отдельно (`ACTOR_PROVIDER`,
  `ACTOR_MODEL`, `JUDGE_PROVIDER`, `JUDGE_MODEL`). **Судья — всегда другая модель, чем актор**;
  проверка при старте, иначе ошибка конфигурации.
- **JSON из ответа модели:** извлечь объект (допускается одна обёртка ```json), валидировать
  Pydantic-схемой хода; при ошибке — одна попытка починки отдельным коротким вызовом
  («верни только исправленный JSON по схеме: ...»); иначе — отказ хода с причиной.
- **Канал ответов человека:** `AnswerChannel` — по `run_id` хранит `asyncio.Future`;
  `ask(questions) -> answers` ждёт до `ANSWER_TIMEOUT_S` (по умолчанию 900).
- **Проверка источников** `validate_card(card, sources: dict[source_id, text]) -> list[Error]` —
  **главный механизм «не выдумывать»**, общий для обоих движков:
  - у каждого непустого поля ≥1 источник; `source_id` существует;
  - `quote` — подстрока текста источника после нормализации (регистр, пробелы, типографские
    кавычки, ё/е, неразрывные пробелы);
  - каждое число, дата, e-mail, телефон, URL, @handle и слово с заглавной буквы не в начале
    предложения (имена, бренды) из `value` встречается в тексте процитированных источников;
  - `value` не длиннее суммы цитат × 3 (защита от «дописывания» пересказом);
  - ошибка = `{field, code, message}`; сообщения человекочитаемые, по-русски — они идут
    модели в фидбэк и в UI.
- **Трасса:** JSONL-событие на каждое действие (`run_started`, `llm_call` с ролью/токенами/
  длительностью, `proposal`, `rejected` с причиной, `committed`, `questions_asked`,
  `answers_received`, `card_validated`, `run_finished`). Трасса — источник для `view`,
  replay, отладки и отчёта сравнения.
- **Короткие id:** все сущности получают короткие id по типу (`P1`, `E3`, `C2`, `Q1`, `A1`).
  Модель никогда не видит и не пишет UUID.
- **Промпты** лежат файлами (`engines/<engine>/prompts/*.md`) и отдаются `contract`-эндпоинтом.

## 4. Лёгкий движок (`engines/light/`)

Цель: **2–5 вызовов модели, до вопросов ≤ 20 с, весь прогон ≤ 45 с** (без учёта времени
человека). Диалектика — фиксированный конвейер с жёсткими схемами, а не свободный выбор ходов.

### 4.1 Конвейер

1. **ANALYZE** (1 вызов актора, JSON-схема):
   ```json
   {"simplest": {"content": "...", "elements": [{"id":"E1","dimension":"...","statement":"...","quote":"..."}]},
    "opposite": {"content": "...", "need": "...", "elements": [{"id":"E5","dimension":"...","statement":"..."}]},
    "contradictions": [{"id":"C1","kind":"gap|conflict","field":"data",
                        "simplest_refs":["E2"],"opposite_refs":["E6"],"statement":"..."}],
    "questions": [{"id":"Q1","text":"...","field":"data","contradiction_id":"C1","why":"..."}]}
   ```
   Структурная проверка кодом: ≥3 элемента у каждой стороны; у элементов простейшего `quote` —
   подстрока черновика; ≥3 противоречия; refs существуют и с нужной стороны; 3–5 вопросов;
   каждый вопрос ссылается на существующее противоречие; каждое противоречие покрыто вопросом;
   вопрос ≤200 символов и содержит ровно один «?».
   Ошибки → 1 повторный вызов с перечнем ошибок; дальше `failed`.
2. **CRITIQUE** (1 вызов судьи, опционально, `LIGHT_JUDGE=1` по умолчанию): проверяет только
   (а) развитие противоположности описывает, что нужно команде для старта (саму противоположность
   судья **не** переоценивает — она задана доменом §1, см. §5.0 п.1), (б) вопросы не подсказывают ответ и
   не спрашивают того, что уже есть в черновике. Вердикт `{"accepted", "issues":[{"target_id","problem"}]}`.
   При `accepted=false` — 1 вызов актора на исправление перечисленных элементов. Сбой судьи
   (пустой/битый ответ после ретраев) → вопросы идут как есть, в метриках `judge_unavailable`.
3. **ASK**: вопросы → `waiting_answers`; ждём человека.
4. **ASSESS + CARD** (1 вызов актора): вход — черновик, граф, ответы с `answer_id`. Выход —
   `{"assessment":[{"contradiction_id","relation":"resolved|not_resolved|new_gap","explanation"}],
   "card": CardDraft}`. Затем `validate_card`. Ошибки → до 2 вызовов исправления **только
   сломанных полей** с построчным списком ошибок; поля, которые не удаётся обосновать, —
   `null` (это честно, а не провал).
5. **Второй круг** (опционально, `LIGHT_MAX_ROUNDS=2`): если есть `new_gap` по полю с весом
   ≥10 и лимит кругов не исчерпан — 1 вызов на 1–3 новых вопроса, снова ASK, затем снова шаг 4.
6. `card_ready`.

### 4.2 GraphView
simplest/opposite → узлы сторон; элементы → `element` с `develops`; противоречия → `contradiction`
с `contradicts` от элементов обеих сторон; вопросы → `question` с `resolves` к противоречию;
ответы → `answer` (`answers`); поля карточки → `field` с `grounds` от ответов/черновика.
Статусы противоречий — по оценке шага 4.

## 5. Тяжёлый движок (`engines/heavy/`)

Цель: **строгий протокол диалектического развития, где каждый шаг — отдельный проверяемый
ход**, с дорожной картой, построенной в мысли до действий, практикой, пересмотром карты и
оценкой скачка по фактическим наблюдениям. Бюджет: ≤ 40 ходов, до вопросов ≤ 90 с, весь
прогон ≤ 4 мин (без времени человека).

### 5.0 Результаты пилота — обязательно учесть

Пилот на ранее существовавшем тяжёлом движке общего назначения (тот же демо-черновик,
скриптованный бизнес, 3 прогона) — **0/3 дошли даже до вопросов**: все упёрлись в лимит
отказов за 87–156 с. Причины и обязательные решения:

1. **Судья отвергал доменную противоположность** («студенческая команда — не независимая
   потребность») до 8 раз подряд: общий философский критерий спорил с доменным определением.
   → Противоположность в этой задаче **известна заранее** (§1). Тяжёлый движок **назначает её
   кодом** из доменной конфигурации сразу после развития простейшего (`seed_opposite`);
   модель её развивает, но не выбирает, и судья её не переоценивает.
2. **Судья требовал от промежуточных ходов готовую карточку** («роль требует полной карточки»),
   потому что видел роль актора с требованием «обязан вызвать инструменты до COMPLETE».
   → Судья получает **только** доменную модель §1, контракт текущего хода и граф — **без**
   инструкций роли актора о финале и инструментах.
3. **BEGIN_EXECUTION отклонялся 7 раз** за «неполный маршрут», хотя маршрут в этой задаче всегда
   один: вопросы → карточка. Модель при этом пыталась сделать несуществующий ход
   `ASK_BUSINESS`. → Маршрут карты **строит код** (`ask_business` → `commit_card` для выбранных
   разрешений); `BEGIN_EXECUTION` проверяется только структурно. Названия ходов действия
   совпадают с доменом: `ASK_BUSINESS` и `COMMIT_CARD` — ходы (их payload — аргументы
   инструмента), а не абстрактный `PROPOSE_ACTION`.
4. Отказы судьи должны быть **исполнимыми**: `issues` — конкретно что поменять в payload; после
   2 отказов одного этапа в промпт актора добавляется короткий образец корректного payload для
   этого хода (образец из доменной конфигурации, не из текущего черновика).
5. Бюджет отказов считается **по этапу** (не более 4 на ход одного типа) и общий (≤ 12);
   `judge_unavailable` в бюджет не входит.

Отсюда таблица ходов §5.2 применяется с поправками: `DESIGNATE_OPPOSITE` — ход кода, не модели;
`PROPOSE_ACTION` заменён на `ASK_BUSINESS` и `COMMIT_CARD`; `BEGIN_EXECUTION` не судится.
Живой тест тяжёлого движка на демо-черновике — **первым делом**, как только работает цикл,
а не в конце.

### 5.1 Состояние

Сущности (короткие id): `Goal`; `Process(id, content)`; `Designation(id, process_id,
role: candidate_simplest|simplest|opposite)`; `Development(id, source_process_id,
emergent_process_id, potential, emergence, concretization)` — развитие как становление
от абстрактного к конкретному, заложенное в источнике, а не «следующая задача»;
`Contradiction(id, simplest_id, opposite_id, simplest_dev_refs, opposite_dev_refs,
unity, status)`; `Resolution(id, contradiction_id, process_id, content, outcome:
replacement|mediation, confirmed_roadmap_id)`; `Roadmap(id, contradiction_ids,
resolution_ids, execution_process_ids, frozen_copy, revision_reason)`;
`Action(id, roadmap_id, origin_process_id, tool, args, expectation, status)`;
`Observation(id, action_id, success, payload, error)`;
`PracticeAssessment(id, observation_id, relation: confirmed|partially_confirmed|contradicted|inconclusive,
explanation, consequence)`; `Completion`. Фаза: `planning|executing|done|failed`.

Все изменения — только через слой коммита: ход сначала валидируется целиком, потом
применяется атомарно (либо всё, либо ничего). Неподтверждённые кандидаты принадлежат своему
предложению и удаляются только вместе с ним.

### 5.2 Ходы

| Ход | Смысл | Структурные условия |
|---|---|---|
| `PROPOSE_SIMPLEST` | кандидат простейшего процесса | нет утверждённого простейшего |
| `ASSESS_SIMPLEST` | утвердить/отклонить кандидата с причиной | есть кандидат |
| `DEVELOP_PROCESS` | развить процесс (любой стороны) | источник утверждён; поля развития непустые |
| `DESIGNATE_OPPOSITE` | назначить противоположность в контексте развития простейшего | простейший развит ≥1 раз |
| `ESTABLISH_CONTRADICTION` | противоречие как единство развития обеих сторон | **обе** стороны развиты; refs принадлежат своим линиям развития |
| `PROPOSE_LEAP` | разрешение противоречия: вопросы бизнесу (новый конкретный процесс, а не «объединить стороны») | есть противоречие без разрешения |
| `BEGIN_EXECUTION` | принять дорожную карту (упорядоченный маршрут исполнения) | есть разрешение; фаза planning; при пересмотре маршрут отличается от прежнего |
| `PROPOSE_ACTION` | действие из процесса маршрута: `ask_business` или `commit_card` | фаза executing; origin — процесс из маршрута; нет ожидающих/неоценённых действий |
| `ASSESS_PRACTICE` | сравнить ожидание с наблюдением | есть неоценённое наблюдение; провал инструмента не может быть `confirmed` |
| `REVISE_WORLD` | вернуться к планированию, сохранив прежние карты и наблюдения | практика противоречит карте; учтены все опровергнутые наблюдения |
| `ASSESS_LEAP` | разрешение реализовано — по фактическим успешным наблюдениям текущей карты | практика оценена, противоречий с картой нет |
| `COMPLETE` | итог: карточка | есть успешное наблюдение `commit_card` текущей карты; все разрешения карты подтверждены; **без хотя бы одного `ask_business` недостижим** |

Правила:
- **Resolver** возвращает разрешённые ходы, повторяя реальные предусловия валидатора
  (ход не предлагается, пока не может закоммититься). В промпт и в схему ответа попадают
  только разрешённые ходы.
- Нет домен-инструментов в фазе planning. Максимум 2 круга вопросов (2 `ask_business` в
  разных картах или одной), дальше разрешён только путь к `commit_card`.
- Неуспешный `commit_card` → `ASSESS_PRACTICE` c `contradicted` → `REVISE_WORLD` или новое
  действие `commit_card` с исправлениями (решает модель, валидатор следит, что повтор не
  байт-в-байт тот же); 3 провала проверки источников → `failed`.
- Ход, отклонённый дважды одинаково, → в следующий промпт идёт явное «СТОП: этот ход не
  разрешён/не проходит по причине X, выбери из списка Y».

### 5.3 Цикл

```
while not done:
    allowed  = resolver.allowed(state)
    prompt   = render(state, allowed)
    proposal = parse_or_repair(await actor.generate(prompt, json_schema=union(allowed)))
    ok, err  = structural.validate(proposal, state)
    if ok and proposal.move in JUDGED: ok, err = await judge.validate(proposal, state)
    if ok: commit(proposal, state); if tool move: observation = await tool(...)
    else:  record_rejection(err)
    check budgets: max_iterations=40, max_rejections=8, deadline
```
`JUDGED` = `PROPOSE_SIMPLEST`, `DEVELOP_PROCESS`, `ESTABLISH_CONTRADICTION`, `PROPOSE_LEAP`,
`ASSESS_PRACTICE`, `REVISE_WORLD`, `ASSESS_LEAP`. Только кодом: `ASSESS_SIMPLEST`,
`DESIGNATE_OPPOSITE` (ход кода, §5.0), `BEGIN_EXECUTION`, `ASK_BUSINESS`, `COMMIT_CARD`, `COMPLETE`. Остановка по бюджету/дедлайну — честная,
с сохранённым графом, без принудительных одобрений.

### 5.4 Промпт актора (строго)

Состав: (1) инструкция протокола и доменной модели §1; (2) черновик как цель; (3) текущее
состояние **один раз**, компактным текстом с короткими id; (4) наблюдения текущей карты
целиком; (5) последний отказ (одна строка) и, при повторе, СТОП-подсказка; (6) «подсказка
следующего шага» — что структурно не хватает (например: «противоположность не развита —
предложи DEVELOP_PROCESS для P4; ESTABLISH_CONTRADICTION пока недостижим»); (7) схемы только
разрешённых ходов; (8) бюджет итераций. **Не включать** историю событий, замороженные копии
карт и дубль состояния в другом формате — они растут с каждым ходом и раздувают стоимость
(в нашем прошлом опыте такое удаление сократило токены на ~40% и **повысило** долю
успешных прогонов).

### 5.5 Судья

Вход: ход, его контракт, текущий граф (без истории событий), доменная модель §1, черновик.
**Не передавать** судье роль актора с требованиями к финалу и инструментам (§5.0 п.2).
Выход строго `{"accepted": bool, "reason": str, "issues": [str]}`. Узкие критерии по ходу
(судья проверяет **только критерий этого хода**, не полноту итоговой карточки):
- SIMPLEST — выведен из черновика, порождающий; ASSESS_SIMPLEST — обоснованное суждение;
- DEVELOPMENT — конкретизация, заложенная в источнике, из текста черновика (для простейшего);
- OPPOSITE — не судится: задана доменом (§5.0 п.1). Судится только её развитие: описывает,
  что нужно команде для старта, а не пересказывает простейший;
- CONTRADICTION — единство развития обеих сторон, опирается на указанные элементы;
- LEAP — вопросы конкретны, один факт, не подсказывают ответ, не повторяют черновик,
  разрешают названное противоречие;
- BEGIN_EXECUTION — маршрут связный и исполнимый;
- PRACTICE — оценка соответствует тому, что человек реально ответил / что вернула проверка;
- REVISE_WORLD — наблюдения действительно требуют изменить карту;
- ASSESS_LEAP — реализация подтверждена фактическими наблюдениями.
Сбой судьи (пустой/битый ответ после ретраев) → ход отклоняется с `judge_unavailable`; эта
пометка **не попадает** ни в фидбэк актору, ни в вход судьи дальше (иначе один сбой
провайдера каскадом отравляет все следующие вердикты — наблюдалось на практике).

### 5.6 GraphView
Процессы → `simplest`/`opposite`/`element` по назначению и линии развития; противоречия,
разрешения-вопросы, ответы, поля карточки — как в §4.2; отклонённые ходы в граф не попадают.

## 6. Ловушки (правила, выученные на практике)

1. Длинные id модели путают и выдумывают → только короткие алиасы.
2. Ходы, недоступные сейчас, но упомянутые в промпте, притягивают модель → показывать только
   разрешённые, resolver зеркалит реальные предусловия.
3. Модель колеблется между двумя преждевременными ходами, не повторяя один и тот же → нужна
   проактивная «подсказка следующего шага», а не только реакция на повторы.
4. Судья отклоняет промежуточный ход за неполноту итога → в промпте судьи явное правило
   «только критерий этого хода» с примерами принять/отклонить.
5. Сбой провайдера ≠ вердикт; история отказов не передаётся судье.
6. Всё, что ждёт человека, — через канал ответов с собственным длинным таймаутом;
   таймауты вызовов модели (~60–90 с) и ожидания человека (~900 с) — раздельные.
7. Провайдеры падают (DNS, 429, пустые ответы): ретраи, fallback, `health`, replay.
8. Один прогон = свой экземпляр состояния; никакого общего изменяемого состояния между прогонами.
9. Судья, видящий требования к итогу, отклоняет промежуточные ходы за «неполноту» →
   давать судье только критерий текущего хода и доменную модель (подтверждено пилотом §5.0).
10. Если доменное понятие известно заранее (здесь — противоположность и маршрут), фиксировать
   его кодом, а не заставлять модель «угадать» его под строгим судьёй.
11. Модель склонна «пересказывать красиво» и добавлять правдоподобные детали → проверка
   источников — кодом, а не просьбой в промпте.

## 7. Тесты

### 7.1 Общий conformance-набор (`tests/conformance/`, без сети, параметризован по движку)
Один и тот же набор прогоняется для `light` и `heavy` через `ScriptedLLM` (у каждого движка
свой скрипт ответов модели) и скриптованного «бизнеса»:
- счастливый путь: `analyzing → waiting_answers → building_card → card_ready`; ≥3 вопросов;
  у каждого вопроса есть `contradiction_id`, существующий в `GraphView`; `points_at_stake`
  = веса из запроса;
- карточка проходит `validate_card`; поле без сведений = `null`;
- выдуманный факт в поле карточки (число, e-mail, имя) → движок не отдаёт его в `card`
  (исправляет или ставит `null`), в трассе видна причина;
- битый JSON модели → починка или честный отказ; бюджет отказов → `failed` с графом;
- сбой судьи не появляется в фидбэке актору;
- таймаут человека → `failed` c `stop_reason="answer_timeout"`, граф сохранён;
- два параллельных прогона не мешают друг другу; `cancel` работает;
- `view` не делает сетевых вызовов; `GraphView` валиден по схеме.

### 7.2 Юнит-тесты
`validate_card` (каждое правило, нормализация), JSON-извлечение/починка, резолвер и валидатор
тяжёлого движка (каждое предусловие каждого хода — позитивный и негативный случай; атомарность
коммита), конвейерная валидация лёгкого (§4.1).

### 7.3 Живые тесты (opt-in, `RUN_LIVE=1`)
5 синтетических черновиков разной полноты и отраслей (включая демо-черновик: «Хотим чат-бота
на ИИ для наших клиентов, чтобы меньше звонили в поддержку. Данных пока нет. Нужно к
следующему месяцу.»), к каждому — скриптованные ответы бизнеса по полям (на часть полей —
«не знаю»). Каждый черновик × 3 прогона × 2 движка. Инварианты как в 7.1. Провал из-за
недоступности провайдера — `skip` с причиной, а не провал движка.

## 8. Стенд сравнения (`bench/compare.py`)

Запуск: `python -m bench.compare --engines light heavy --repeats 3 --out bench_runs/<дата>`.
Для каждого прогона фиксируется и сводится в `report.md` + `report.json`:

| Метрика | Как считается |
|---|---|
| Доля прогонов до `card_ready` | по статусу |
| Время до первых вопросов, полное время | из трассы |
| Вызовы LLM и токены по ролям | из трассы |
| Отказы ходов, из них `judge_unavailable` | из трассы |
| Проверка источников с первой попытки | `card_validated` |
| Полнота карточки | доля непустых полей из тех, на которые бизнес дал сведения |
| Выдуманные факты | 0 по построению; тест подсовывает ловушки и считает, сколько поймано |
| Уместность вопросов | слепая оценка третьей моделью по рубрике 1–5: конкретность, один факт, не повторяет черновик, связь с противоречием; плюс поле для ручной оценки человеком |
| Покрытие противоречий | доля противоречий `conflict` в черновике (размечены в данных), найденных движком |

Итог отчёта — таблица light vs heavy по черновикам и рекомендация, какой движок ставить в
демо, с честной оговоркой о размере выборки.

## 9. Команда агентов и порядок работы

Каждый агент — в своей ветке/worktree, **владеет своими файлами**; чужие — только через лида.

**Шаг 0 — лид.** Каркас `engines/common`, `engines/light`, `engines/heavy`, `tests/`, `bench/`;
`engines/common/contracts.py` (§2.1), `Engine` Protocol и `get_engine` (§2.2), каркас
HTTP-сервиса (§2.3) с заглушечным движком `echo`, который проходит happy path conformance-теста
на фиксированных данных — чтобы человек мог **сразу** подключать базу к контракту. Коммит.
Контракты заморожены; изменения — только через лида с уведомлением всех (и человека: база
зависит от контракта).

Затем:

| Агент | Владеет | Результат | Готово, когда |
|---|---|---|---|
| A. Общий слой | `engines/common/` (кроме contracts) | §3 | юнит-тесты `validate_card`, JSON, LLM-клиентов на моках HTTP; `ScriptedLLM`; трасса; канал ответов; replay |
| B. Лёгкий движок | `engines/light/` | §4 | conformance зелёный для light; живой демо-черновик ≥2/3 до `card_ready`; метрики §4 |
| C. Тяжёлый движок | `engines/heavy/` | §5 | юнит-тесты резолвера/валидатора/коммита; conformance зелёный для heavy; живой демо-черновик ≥2/3 |
| D. Тесты, данные, стенд, доки | `tests/conformance/`, `tests/live/`, `bench/`, `data/`, `README.md` | §7, §8 | conformance-набор готов до движков (TDD); 5 черновиков с ответами и разметкой противоречий; стенд сравнения; README: контракт, запуск, диаграммы обоих движков |

B и C стартуют сразу на `ScriptedLLM` и интерфейсах из шага 0, не дожидаясь A (A сначала
отдаёт `ScriptedLLM` и `validate_card` — это первый приоритет A).

Точки интеграции (лид):
1. `echo`-движок + контракт → человек подключает базу.
2. Light проходит conformance → переключаем базу на `ENGINE=light`.
3. Heavy проходит conformance → `ENGINE=heavy`.
4. Стенд сравнения на живых провайдерах → отчёт и рекомендация человеку.

Правила для всех:
- Никакого заимствованного кода (см. правило происхождения).
- Никаких моков в production-путях, кроме `ScriptedLLM` в тестах и `ENGINE_REPLAY`.
- Отчитываться фактами: что запускал, что прошло/упало (с выводом), что пропущено.

## 10. Критерии приёмки

- [ ] База может подключить любой движок одной переменной `ENGINE`, через Python API или HTTP.
- [ ] Оба движка проходят один и тот же conformance-набор без сети.
- [ ] На демо-черновике оба выдают ≥3 вопроса, каждый связан с противоречием в графе, с «+N баллов».
- [ ] Ни одно поле карточки не содержит факта вне черновика и ответов (тест-ловушки пройдены).
- [ ] `contract`-эндпоинт показывает промпты, схемы и реальный пример обработки битого ответа.
- [ ] `health`, честные `failed` со `stop_reason`, replay работают.
- [ ] Живой отчёт сравнения light vs heavy: доля успехов, время, токены, уместность вопросов,
      покрытие противоречий, рекомендация.
- [ ] Целевые метрики §4 и §5 достигнуты или честно указано, насколько нет.

Начни с шага 0. Перед раздачей задач кратко перескажи человеку контракт §2 — он нужен ему
для базы в первую очередь.
