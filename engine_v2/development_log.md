# Log of Dialectical Development (Process Memory)

*This document serves as the Memory of the development process itself. According to Rule 4, before each new step, we are required to refer to this log to maintain continuity.*

> **Dual Role of the Document:**  
> DialecticAI is being developed according to the same principles that a developer will later use to create agents with its help. Therefore, `development_log.md` simultaneously serves as:  
> 1. The memory of the framework's development — it records why specific architectural decisions were made.  
> 2. A living example for agent developers: this is how the log should look when creating an agent using DialecticAI.  
> Consequently, every significant step in the framework's development must be recorded here — with the same level of reflection that we require from users.

> **Template for significant steps (Rule 5 — Driving to Contradiction), added after 2026-09-12:**
> Routine steps may keep the lighter `Reality Check` / `Transition Evaluation` / `Implementation` format used throughout this log. A step that is a *fundamentally new architectural step* (Rule 3's threshold) should additionally name, in this order: **Simplest process** → **Development (abstract → concrete)** → **Opposite process** (not an alternative practice — see Rule 5) → **Contradiction** (the two taken in unity) → **Leap** (the resolving process). See the `[2026-09-04] Step 6` entry below for a worked example.


## [2026-09-01] Step 1: System Prompt (Thesis)
- **What was done:** Formulated the identity of the AI Tutor (`tutor_prompt.md`).
- **Logic:** The tutor does not provide ready-made answers but analyzes the student's mental model and generates guiding questions (Antithesis).

## [2026-09-01] Step 2 and 3: Interaction Mechanism and Action
- **What was done:** Wrote the basic script `tutor_agent.py`.
- **Reality Check:** Realized that regular text output does not allow the code to separate the agent's thoughts from the user's response and extract states.
- **Evaluation and Synthesis:** Made the prompt (Step 1) return strict JSON. The input-output logic began to be dictated by the structure of the prompt.

## [2026-09-02] Step 4: Agent Memory (Knowledge Graph)
- **Reality Check (Time):** If the dialogue lasts many turns, the agent forgets the student's progress. It needs a history.
- **Transition Evaluation (Best Practices):** Instead of simply passing the chat history (memory buffer) or a vector database, we chose the **Knowledge Graph** as the ideal practice for the tutor.
- **Implementation:** Added the `KnowledgeGraphMemory` class, which is updated from the agent's JSON response.

## [2026-09-02] Meta-Solution (Framework Strategy)
- **Context:** Realized that our principles form a unique framework for building agents.
- **Solution (From Specific to Abstract):** First, we fully go through all stages of creating an agent with a specific example (Tutor), perfect it, and then refactor (abstract) this experience into a universal framework.

## [2026-09-03] Step 5: Tools (Tools / External Actions)
- **Reality Check (Agent Blindness):** Realized that the LLM might mistakenly consider the sent code correct. Without actually running the code, the tutor is blind to physical reality and can give false praise.
- **Transition Evaluation (Best Practices):** Applied the industry practice of **ReAct (Reason + Act)**. One user message now generates a hidden micro-cycle for the LLM: Analysis -> Tool Call -> Result (Observation) -> Final Synthesis (Response).
- **Implementation:** Added `tool_calls` to the JSON schema of the prompt. Added `ToolRegistry` to the agent's code and a `while` loop that intercepts tool requests and returns execution errors to the agent.

## [2026-09-04] Step 6: Birth of the Framework (Destruction of the Tutor) — Rule 5 worked example
*(Reformulated later, when Rule 5 — "Driving to Contradiction" — was added to `dialectics_rules.md`, to show what a significant-step entry should look like going forward. The original one-line "Dialectical Leap" note is expanded here, not replaced in spirit.)*
- **Simplest process:** "Building one working Tutor agent" (goal → prompt → JSON-structured turn → tool call → memory update) — every later capability of the framework (Layers 0-6) is traceable back to a decision first made concretely for the Tutor.
- **Development (abstract → concrete):** Tutor identity (Step 1) → structured JSON turn (Step 2-3) → memory across turns (Step 4) → tools / Reality Check (Step 5). Each step already contained the next in potential form: strict JSON output was needed the moment we wanted to separate "thought" from "answer," and memory was needed the moment JSON gave us discrete, storable turns.
- **Opposite process:** "Writing a second, different agent (e.g., a Coder) by copying and hand-editing the Tutor's script." This process does not need the Tutor's specific concrete code to exist — it only needs *a* working example to imitate, and its natural end-state is N disconnected scripts, none of them reusable as a base class.
- **Contradiction:** the Tutor-as-concrete-agent (simplest process, keeps growing more specific features) and copy-to-create-a-new-agent (opposite process, treats the Tutor as disposable scaffolding rather than universal ancestor) taken together — the framework cannot keep deepening the Tutor's specifics *and* also let every new agent start from a fresh copy; the two directions could not develop side by side.
- **Leap:** `DialecticalAgent` — a base class that does not replace the Tutor's lessons or the copy-instinct's practicality separately, but absorbs both: it generalizes what the Tutor already proved (goal → prompt → memory → tools contract) into something a Coder or Analyst can inherit without copying code. The Tutor's own script is deleted precisely because its content survives, abstracted, in the new base class.
- **Action:** Removed the old Tutor code (`tutor_agent.py`, `tutor_prompt.md`). Began the abstract framework architecture, subordinated exclusively to the derived rules. The Tutor was recreated later as the first test instance built on `DialecticalAgent`.

## [2026-09-06] Layer 5 (Refinement) ✅: Dashboard on FastAPI + WebSockets

- **Reality Check (http.server Limitation):** The standard `http.server` from stdlib works synchronously. This makes it impossible to stream the agent's state to the browser without constant polling from the client — a gross violation of UX and architectural purity.
- **Transition Evaluation (Best Practices):** Considered:
  - `aiohttp` — a full async framework, but excessive for the dashboard, and lacks built-in OpenAPI.
  - `Starlette` — a minimalist foundation for FastAPI; a reasonable alternative, but lacks the conveniences of FastAPI.
  - **FastAPI + Uvicorn** — chosen as the best balance: native WebSockets, built-in documentation, widely adopted in the industry.
  - SSE (Server-Sent Events) without WebSocket — simpler, but only one-way communication (server → client), which limits interactive chat.
- **Solution:** FastAPI with WebSocket endpoint `/ws/stream`. The client receives real-time updates of traces.
- **Moved to an optional package:** `dialectic_observability` — to not violate the Zero-Dependencies principle of the core.

## [2026-09-06] Refactoring ✅: Moving LLM Clients to `integrations/`

- **Reality Check (Core Bloat):** `core/llm.py` had grown: Gemini, OpenAI, FallbackLLM — all in one file. Importing from `core` began to pull in provider logic even where it was not needed.
- **Transition Evaluation:** Considered:
  - Keeping everything in `core/llm.py` — simple, but violates the single responsibility principle.
  - Separate package `providers/` — standard practice in LangChain, but semantically inaccurate.
  - **`integrations/`** — chosen: the name directly signals "these are external integrations, not core."
- **Implementation:** `integrations/gemini/llm.py`, `integrations/openai/llm.py`. In `core/__init__.py`, deprecation aliases were left for backward compatibility.

## [2026-09-07] Refactoring ✅: Transition to asyncio (`async def run()`)

- **Reality Check (Blocking):** `DialecticalEngine.run()` makes HTTP requests to the LLM API. In synchronous mode, this blocks the event loop — it is impossible to run multiple agents in parallel and integrate the engine into async servers (FastAPI).
- **Transition Evaluation (Best Practices):**
  - `trio` — an alternative async library, stricter, but incompatible with the standard asyncio ecosystem.
  - `anyio` — an abstraction over asyncio/trio; excessive without a real need to support both runtimes.
  - Synchronous wrapper `asyncio.run()` from the outside — would maintain compatibility but would hide the nature of operations.
  - **Native `async def`** — chosen: an honest representation of what the engine does IO. Users who need a synchronous interface can wrap it themselves using `asyncio.run()`.
- **Consequences:** `run_tutor.py` and `cli/main.py` were updated for correct invocation via `asyncio.run()`.

## [2026-09-07] Refactoring ✅: Migration of Schemas to Pydantic v2

- **Reality Check (Invalid Data from LLM):** `dataclasses` do not perform runtime type validation. The LLM could return `tool_calls` as a string instead of a list — and the code would fail in an unpredictable place without a clear error message.
- **Transition Evaluation (Best Practices):**
  - `marshmallow` — a mature serialization library, but heavier to use and does not provide IDE hints.
  - `attrs` — more compact than dataclasses, but without built-in type validation.
  - `TypedDict` — without validation, only for annotations.
  - **Pydantic v2** — chosen: the de facto standard for FastAPI, Rust core (performance), strict runtime validation, excellent IDE integration.
- **Compromise:** Pydantic is added as a core dependency (not optional). This is a conscious violation of Zero-Dependencies, justified by the fact that without schema validation, the framework is unreliable.
- **Implementation:** `core/schema.py` rewritten to `BaseModel`. `CollisionResult` marked as `DEPRECATED`, added `Evidence`.

## [2026-09-08] Layer 3 (Refinement) ✅: ClaimValidator — Phase 4 (VALIDATE)

- **Reality Check (Hallucinations in Synthesis):** The agent could refer to a non-existent `evidence_id` or distort a fact during synthesis. `DialecticalEngine` did not check the correctness of claims.
- **Transition Evaluation:**
  - Rule-based hallucination check — can be implemented without LLM, but only covers primitive cases.
  - RAG-based validation — requires a vector database, excessive.
  - **LLM-as-a-judge (Fact-Checker)** — chosen: flexible, scalable, aligns with industry practice of LLM Evaluation.
- **Conscious Contradiction:** The validator itself is an LLM and can also make mistakes. This is recorded in `@dialectical(own_contradictions=...)` of the `ClaimValidator` class.
- **Implementation:** `engine/validator.py`. The engine calls it optionally — only if `claim.requires_validation=True`.

## [2026-09-08] Layer 2 (Expansion) ✅: WebFetchCheck and MCPTool

## [2026-09-13] Layer 6 (Refinement) ✅: DialecticalArchitect — moving Rule 5 off the developer

- **Simplest process:** A developer states an agent's goal in plain language, with no dialectical vocabulary — `cli/creator.py`'s wizard used that raw goal verbatim.
- **Development (abstract → concrete):** raw goal → tool selection → LLM choice (existing wizard) → (new) an automatic design pass that turns the raw goal into a refined one → generated agent script/config.
- **Opposite process:** Asking the developer to author the Simplest/Development/Opposite/Contradiction/Leap analysis themselves before creating an agent — a process that needs no automated reasoning at all, only developer literacy in dialectics. This does not require the framework's own generative machinery to run; it only requires a philosophically-literate developer.
- **Contradiction:** Every framework-produced agent should be dialectically designed (Rule 1: Generative Beginning), yet the developer creating it should not need to know what dialectics is — self-authored rigor and developer simplicity cannot both be satisfied by the same person doing the work.
- **Leap:** `DialecticalArchitect` (`dialectic_ai/cli/architect.py`) — a component that runs the full Rule 5 procedure itself, in one LLM call, from the developer's plain-language goal and tool list, and hands back only an ordinary refined goal plus an auditable log. Neither side of the contradiction is discarded: the developer keeps total simplicity, and the framework keeps its rigor — the rigor is simply relocated from the human to the machine.
- **Implementation:** `cli/creator.py`'s wizard gained one plain-language yes/no question ("Refine the goal automatically now?") after the existing LLM-choice step; on acceptance it builds a live LLM instance, calls `DialecticalArchitect.design(...)`, and (a) uses the refined goal in the generated agent, (b) writes `<agent>_development_log.md` next to it, readable without any new plumbing by the existing `DialecticalAuditor.audit_agent(log_path=...)`.

Full suite: 73 passed, 1 skipped.

## [2026-09-13] Bug fix: repair-schema blindness and silent empty-turn stall in `DialecticalEngine`

- **Reality Check:** Ran a real GAIA2 "ambiguity" scenario end-to-end (GigaChat-Pro as the agent LLM). The agent got the right answer internally on iteration 1 ("No contacts in Prague are between the ages of 40 and 48.") but its raw output was plain prose, not JSON. From there it looped for **~28 iterations and ~30 minutes wall-clock**, repeating almost the exact same non-answer every time, until `max_iterations` cut it off as a hard failure.
- **Root cause #1 (`engine/repair.py`):** `JsonRepairer.repair()` asked the LLM to "conform exactly to the required JSON schema" but never actually included that schema in the repair prompt. The repair call dutifully returned valid JSON — with field names it invented itself (`contacts`, `criteria`, `result`, `message`) instead of the framework's real ones (`decision`, `response`, ...). `ParsedLLMResponse`'s pydantic model silently drops unrecognized keys, so `to_dict()` (which uses `exclude_unset=True`) came back as a bare `{}`. The repair reported "successful" while discarding the answer entirely.
- **Root cause #2 (`engine/executor.py`):** When a turn produces neither `tool_calls` nor `response` (exactly what root cause #1 was quietly producing), `run()` fell through the bottom of the loop body without appending anything to conversation history. The next LLM call therefore saw an unchanged prompt and reproduced almost the same non-JSON answer — and the existing "idle loop" safety net compared `decision + hypothesis` text for exact equality, which minor LLM phrasing variance across repair attempts defeated, so it never fired.
- **Fix:** (1) `JsonRepairer`'s prompt now embeds the actual schema (`agent/prompt_builder.py`'s `FORMAT_INSTRUCTION`, exported for reuse) and explicitly tells the model to reuse those exact field names; a repair that still comes back schema-empty now raises `ControlledRepairError` instead of succeeding silently. (2) `DialecticalEngine.run()` now detects an "empty turn" (no tool_calls, no response) directly, pushes an explicit corrective message into history on the first occurrence, and folds this signal into the existing idle-loop counter (independent of the fragile text-equality check) so a second consecutive empty turn forces synthesis instead of consuming the full iteration budget.
- **Verification:** Reproduced the exact failing raw text against `JsonRepairer` directly — 3/3 repairs now correctly populate `response` (previously 3/3 came back `{}`). Reproduced the full failure through `DialecticalEngine.run()` with a test double that forces the first LLM call to return the real broken text: before the fix this was the ~28-iteration/~30-minute stall; after the fix, `status=completed` in **3.1 seconds across 2 LLM calls**. Full suite: 73 passed, 1 skipped; `tests/local_runner.py` sandbox unaffected (3/3 scenarios `completed`).
- **Own contradictions:** This closes the specific failure mode observed with GigaChat-Pro (no native tool calling, more prone to prose fallback), but any provider that fails its first JSON parse could have hit the same schema-blindness bug — it was latent, not GigaChat-specific, just rarely exercised by providers with `response_format: json_object` support. The corrective-message nudge assumes the model can act on plain-English feedback; a model that ignores it entirely still terminates safely (bounded at 2 empty turns instead of 30), but won't necessarily recover the original answer.

## [2026-09-13] Layer 3 (Refinement) ✅: Hard dialectics in the core engine, and driving a second-order contradiction to resolution

- **Simplest process:** A GAIA2 benchmark run (5 real "ambiguity" scenarios, GigaChat-Pro) scored 0% — not from infrastructure failure, but because the single-agent `DialecticalEngine` loop only borrowed dialectical vocabulary (Thesis/Antithesis/Synthesis labels) without running the actual Rule 5 procedure. It treated whole tasks as uncertain instead of decomposing them into unambiguous parts (to act on) and genuinely unclear parts (to ask about) — e.g. an agent asked permission to send an email the user had explicitly and unconditionally instructed it to send, only because an unrelated calendar lookup came back empty.
- **Development (abstract → concrete):** (1) Made `opposite_process`/`contradiction`/`leap` structural, required fields on every finalized `AgentOutput`, in `core/schema.py`/`engine/parser.py`, with prompt text in `agent/prompt_builder.py` rewritten around the real Rule 5 vocabulary instead of Thesis/Antithesis/Synthesis. (2) `DialecticalEngine._phase_synthesize` flags (but does not block on) a `response` given without them — `dialectical_resolution_missing`. (3) Live-reproduced the Yoga scenario: the model *did* fill the fields, even wrote `leap: "Decomposition: ..."` — and still asked permission for the unconditional email anyway. The claim and the actual `tool_calls` had diverged; nothing checked for that.
- **Opposite process:** Treating the mismatch between a claimed `leap` and the actual `tool_calls` taken as just another passive audit metric (a flag recorded in `trace.jsonl` for a human to notice later) — a process that does not need the engine's own generative loop to do anything about it, only needs a human reading reports afterward.
- **Contradiction:** The framework's own Rule 5 says a contradiction must be *driven to resolution*, not just recorded — yet the engine, on detecting its own agent's claim/action mismatch, was doing exactly the passive thing Rule 5 argues against: logging it and moving on.
- **Leap:** Added a structural `leap_type` field (`"decompose_and_act" | "ask_only" | "fully_resolved"`, checkable against `evidence_store` — not keyword-matched against free text) to `core/schema.py`/`engine/parser.py`. When `leap_type == "decompose_and_act"` but `evidence_store` is empty (nothing was ever actually done), `DialecticalEngine.run()` now treats this as a second-order contradiction and feeds it back into the *same generative loop* — pushes an explicit corrective message (including a demand for self-diagnosis: which of your own earlier steps led here) into history and `continue`s, bounded to one retry (reusing the same bounded-nudge pattern already proven safe for the empty-turn bug above), instead of silently finalizing with a passive flag.
- **Backward-tracing companion:** Since finding *this* required manually re-running the scenario, reading raw JSON, and tracing back through `repair.py`/`prompt_builder.py` by hand, the same forensic work was formalized: `dialectical_resolution_missing`/`leap_action_mismatch` trace events now carry the full raw response, full prompt, and provider class (not a 200-char preview), and a new `DialecticalAuditor.investigate_contradiction()` (wired to `dialectic audit --investigate`) reads one such event plus the actual framework source files in the processing chain and asks an LLM for a root-cause hypothesis — diagnostic only, does not modify code or re-run the agent.
- **Reality Check:** New test (`test_dialectical_engine_drives_leap_action_mismatch_back_into_development`) proves the loop-back: a `MockLLM` sequence that first claims `decompose_and_act` with no tool call is forced back into development, only finalizing after a real tool call appears in `evidence_store`. Live-verified `investigate_contradiction` against a real captured GigaChat trace: it correctly diagnosed the failure as "the agent did not decompose the task into its two independent parts" and flagged it as a systemic gap, not a one-off. Full suite: 75 passed, 1 skipped.
- **Own contradictions:** The `leap_type` enum is a coarse, three-way signal — it catches "claimed action, took none" but not subtler mismatches (e.g., a `leap_type="ask_only"` that unnecessarily blocks an unambiguous sub-action). `investigate_contradiction`'s hypotheses are only as good as the judge LLM and are advisory, not automatically actionable — closing the loop from hypothesis to actual code fix is still a human (or a follow-up session's) decision, by design, not automated.
- **Closing the loop:** `investigate_contradiction`'s hypothesis ("agent did not decompose the task into its independent parts... insufficient guidance") was itself acted on, not left as a report to file away. Added one concrete worked example to `_AGENT_DIALECTICAL_RULES` (`agent/prompt_builder.py`) mirroring the exact Yoga scenario pattern (one unconditional imperative + one genuinely blocked sub-task), contrasting the wrong behavior (ask about everything once one part is blocked) against the right one (act on the unconditional part, narrow the question to the specific blocked part). Re-ran the live Yoga reproduction 3/3 times post-fix: the email was sent in all 3 (0/many before), with `leap_type="fully_resolved"` and no contradiction flags. This is the diagnostic→fix→re-verify cycle the mechanism above exists to enable — the investigation is not the endpoint, acting on it is.

## [2026-09-14] Bug fixes: wrong simulated date in GAIA2 (a year off) and a real `ControlledRepairError` crash

- **Reality Check:** Re-ran the same 5 GAIA2 scenarios after the worked-example fix above. Still 0/5, but the Yoga scenario now genuinely sent the email (the prompt fix worked) — and the oracle expected ZERO emails, revealing the underlying assumption behind the worked example was calibrated on a wrong fact. Separately, `scenario_universe_26_n5mmwn` crashed outright with `ControlledRepairError`.
- **Root cause #1 (`benchmarks/gaia2/adapter.py`):** `env_time` was computed via `hasattr(scenario, "environment") and hasattr(scenario.environment, "get_time")` — verified against ARE's actual `Scenario`/`ScenarioImportedFromJson` classes, `environment` does not exist as an attribute anywhere in that API. This check was **always False** for every scenario ever run, silently falling back to a hardcoded `"2023-10-04 12:00:00"`. Pulled the Yoga scenario's raw data directly from the HuggingFace dataset: its real `start_time` is `1728975600.0` → **2024-10-15**, a full year off from the hardcoded fallback, and its calendar has 365 real events, all dated in 2024. Every "this week"/"today" calendar query the agent ever issued in this benchmark was silently querying the wrong year — explaining the recurring "0 events found" pattern across multiple different scenarios, not just Yoga.
- **Root cause #2 (`engine/executor.py`):** `_phase_collide` injected the full, uncapped string of every successful tool result into conversation history (e.g. a 16-apartment listing, ~7000+ characters), resent in full on every subsequent turn. Compounding across a few turns, plus the larger required Rule 5 fields, pushed GigaChat-Pro past its effective context budget -- its OUTPUT was silently truncated mid-JSON (visible raw text ending mid-sentence, e.g. `"plan_steps": [` with nothing after), which then failed to parse *and* failed to repair (the repair call hit the same truncation), crashing the scenario with an uncaught `ControlledRepairError` instead of a graceful validation failure.
- **Fix:** (1) Use `scenario.start_time` (the real Unix timestamp ARE actually exposes) instead of the always-false `scenario.environment.get_time()` path. (2) Cap injected tool-result text at 3000 characters with a truncation note suggesting offset/limit/search arguments if the tool supports them -- the full content still lives in `evidence_store` for validation, only what's resent to the LLM every turn is capped. ## [2026-09-14] Bug fixes: array/int/bool type-classification bug and unresolved-placeholder tool calls (`benchmarks/gaia2/adapter.py`)

- **Reality Check:** Re-ran the fixed benchmark. - **Fix:** (1) Reordered the classification chain to check container types (`list`, `dict`) before scalar types (`str`, `int`, `float`, `bool`) -- verified directly that `recipients` is now classified `"array"` and a plain string value is correctly coerced to a one-element list, turning a real API call from a hard type-error into success. (2) Added the same coercion pattern for `int`/`float`/`bool` string arguments. (3) Added generic `{{...}}` placeholder detection in `AREToolWrapper.execute()` returning a clear corrective error, and (4) documented the parallel-execution semantics explicitly in `_AGENT_DIALECTICAL_RULES` so this is now a stated rule for every agent built on this framework, not a GAIA2-specific patch.
