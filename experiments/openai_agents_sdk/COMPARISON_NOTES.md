# Сравнительный архитектурный анализ: OpenAI Agents SDK vs DialecticAI

Данный документ содержит объективный архитектурный анализ между официальным **OpenAI Agents SDK** (`openai-agents`) и развивающимся фреймворком **DialecticAI**. Сравнение проводится по ключевым механизмам агентных систем с целью выявления архитектурных альтернатив без субъективных оценок «лучше/хуже».

---

## 1. Определение агента (Agent Definition)

### OpenAI Agents SDK
- **Как реализован:** Декларативный класс-контейнер, объединяющий идентификатор, системную инструкцию, список доступных инструментов, список разрешенных переходов (handoffs), модель и схему выходных данных.
- **Какие классы/API используются:** `agents.Agent(name, instructions, tools, handoffs, model, output_type, hooks, ...)`.
- **Что SDK предоставляет автоматически:** Автоматическую генерацию системного промпта, регистрацию мета-инструментов для handoffs, привязку guardrails и валидаторов.
- **Что приходится писать разработчику:** Текст инструкций, список функций-инструментов и перечень целевых агентов для передачи управления.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/agent/base.py` (`DialecticalAgent`).
- **Как он реализован:** Класс-наследник `DialecticalObject` с обязательным декоратором `@dialectical(origin=..., contradiction=..., resolves=..., generates=..., own_contradictions=..., layer=1)`. Инкапсулирует `goal`, `llm`, `memory`, `tools`, `history`.
- **Какая архитектурная идея используется:** Философско-методологическое принуждение: агент не просто выполняет инструкцию, а обязан размышлять в терминах гипотезы, противоположного процесса, противоречия и скачка (Rule 5). Без декларации архитектурных противоречий класс не инстанцируется.

### Различие
В OpenAI Agents SDK агент — это прагматичный узел графа переходов с фиксированным контрактом API. В DialecticAI агент — это субъект диалектического процесса, несущий в себе кодовые ограничения на структуру мышления и обязательное сохранение опыта в память.

---

## 2. Системные инструкции (System Instructions)

### OpenAI Agents SDK
- **Как реализован:** Передача строки или динамической функции `instructions(context, agent) -> str`.
- **Какие классы/API используются:** Параметр `instructions` в `Agent`, `DynamicPromptFunction`.
- **Что SDK предоставляет автоматически:** Форматирование инструкций и объединение с описанием доступных инструментов и handoffs в системный блок запроса к модели.
- **Что приходится писать разработчику:** Непосредственные указания роли, ограничений и целей агента.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/agent/prompt_builder.py` (`build_system_prompt`).
- **Как он реализован:** Многослойный конструктор промпта: цель агента (`goal`) + нормативный блок `_AGENT_DIALECTICAL_RULES` (категорический императив Rule 5) + обязательный JSON-контракт ответа + схемы инструментов + выжимка памяти (`get_context()`).
- **Какая архитектурная идея используется:** Инструкции агента жестко регламентированы архитектурой фреймворка: разработчик задает только предметную цель (`goal`), а структура мышления и схема ответа навязываются ядром фреймворка.

### Различие
В OpenAI Agents SDK разработчик свободен в формулировании любого системного промпта (формат свободный, задается разработчиком). В DialecticAI системный промпт является нормативно-закрытым: разработчик дополняет предметную цель, но каркас когнитивных правил и обязательный формат JSON зафиксированы ядром.

---

## 3. Маршрутизация (Routing)

### OpenAI Agents SDK
- **Как реализован:** Маршрутизация первого шага определяется передачей начального агента в `Runner.run(starting_agent=...)`. Последующая маршрутизация делегирована LLM через вызовы handoff-инструментов.
- **Какие классы/API используются:** `Runner.run`, `Agent(handoffs=[...])`.
- **Что SDK предоставляет автоматически:** Создание вызовов функций маршрутизации и цикл передачи хода новому агенту.
- **Что приходится писать разработчику:** Декларацию графа доступных переходов от одного агента к другим.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/multi/router.py` (`AgentRouter`).
- **Как он реализован:** Внешний класс-диспетчер запросов. Регистрирует словарь агентов (`_agents`, `_engines`) и список предикативных правил `(condition_fn, agent_name)`. Содержит методы `add_rule()` и `route()`.
- **Какая архитектурная идея используется:** Внешняя детерминированная диспетчеризация до вызова тяжелых моделей: сопоставление ключевых слов или логических условий без затрат токенов, с fallback-агентом по умолчанию.

### Различие
В OpenAI Agents SDK маршрутизация внутри процесса динамическая и осуществляется самой LLM в рантайме через инструменты передачи хода. В DialecticAI маршрутизация вынесена в отдельный компонент `AgentRouter`, работающий до запуска агентного цикла на основе детерминированных предикатов.

---

## 4. Передача эстафеты (Handoff)

### OpenAI Agents SDK
- **Как реализован:** Первоклассный примитив SDK. Представляет собой передачу всей сессии новому агенту. При этом целевой агент становится основным исполнителем и видит предшествующую историю диалога.
- **Какие классы/API используются:** `agents.handoff`, класс `Handoff`, параметр `Agent(handoffs=[...])`.
- **Что SDK предоставляет автоматически:** Создание инструмента `transfer_to_<agent>`, фильтрацию/сворачивание контекста (`input_filter`, `nest_handoff_history`), генерацию системного уведомления о смене агента.
- **Что приходится писать разработчику:** Список разрешенных связей и опциональные коллбеки `on_handoff`.

### Мой framework
- **Где находится аналогичный механизм:** Прямого аналога концепции Handoff как инструмента смены агента внутри единого контекста нет. Косвенно представлен в `dialectic_ai/reality/delegation.py` (`SubAgentTool`) и в оркестраторе `DialecticalTriad`.
- **Как он реализован:** В `DialecticalTriad` передача данных между агентами (Thesis -> Synthesis, Antithesis -> Synthesis) контролируется строго кодом оркестратора через подстановку текстовых ответов одних агентов в промпт следующего.
- **Какая архитектурная идея используется:** Жесткая топология взаимодействия: вместо произвольного перехода модель поставлена в рамки параллельного независимого зарождения тезиса и антитезиса с последующим арбитражем.

### Различие
OpenAI Agents SDK строится вокруг динамического сетевого графа с передачей эстафеты самой моделью (Handoff). DialecticAI ориентирован на детерминированные топологии (параллельная триада или линейный пайплайн), где смену фаз выполняет программный код супервизора.

---

## 5. Агенты как инструменты (Agents-as-Tools)

### OpenAI Agents SDK
- **Как реализован:** Агент оборачивается в инструмент функции через `agent.as_tool()` или кастомный tool, возвращая результат своей работы вызывающему агенту, не передавая ему управление диалогом целиком.
- **Какие классы/API используются:** `Agent.as_tool()` / функциональные обертки.
- **Что SDK предоставляет автоматически:** Изоляцию поддиалога вспомогательного агента от общего контекста родительского агента.
- **Что приходится писать разработчику:** Описание назначения инструмента для выбора вызывающей моделью.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/reality/delegation.py` (`SubAgentTool`).
- **Как он реализован:** Класс `SubAgentTool` наследует `ActionTool` и при вызове `execute(args)` запускает отдельный `DialecticalEngine(sub_agent).run(...)`, упаковывая ответ в объект `Evidence`.
- **Какая архитектурная идея используется:** Делегирование рассматривается как "столкновение с реальностью" (Collision phase): вызов другого агента трактуется как сбор доказательств (`Evidence`), подлежащих проверке валидатором.

### Различие
В обоих фреймворках идея концептуально совпадает (вызов субагента как сбор фактов). Различие в том, что в DialecticAI результат вызова агента-инструмента строго маркируется как `Evidence` со своим UUID и хэшем для дедупликации и последующей верификации через `ClaimValidator`.

---

## 6. Инструменты (Tools)

### OpenAI Agents SDK
- **Как реализован:** Легковесные функции Python с автоматической интроспекцией сигнатур и типов.
- **Какие классы/API используются:** Декоратор `@function_tool`, класс `FunctionTool`, базовый класс `Tool`, `RunContextWrapper`.
- **Что SDK предоставляет автоматически:** Генерацию JSON Schema (включая Strict Schema), исключение контекстных параметров из схемы (`ctx: RunContextWrapper`), перехват исключений и упаковку их в ответ модели.
- **Что приходится писать разработчику:** Стандартную функцию Python с тайп-хинтами и docstring.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/core/tool.py`, `dialectic_ai/core/decorators.py` (`@dialectical_tool`).
- **Как он реализован:** Базовый класс `Tool(DialecticalObject)` -> `ObservationTool` / `ActionTool`. Декоратор `@dialectical_tool` генерирует класс-наследник. Метод `execute` возвращает строго типизированный объект `Evidence(id, source, content, success, error)`.
- **Какая архитектурная идея используется:** Инструменты разделены по семантике на действия (Action, изменяющие мир) и наблюдения (Observation, считывающие мир). Результат всегда формализован в виде улики (`Evidence`), сохраняемой в `EvidenceStore`.

### Различие
В OpenAI Agents SDK инструменты функциональные и слабосвязанные: обычная функция Python возвращает произвольные данные (строку, словарь, объект). В DialecticAI инструмент возвращает контрактную структуру `Evidence`, которая регистрируется в хранилище доказательств и участвует в контроле честности агента ("говорит vs делает").

---

## 7. Оркестрация (Orchestration)

### OpenAI Agents SDK
- **Как реализован:** Цикл управления возложен на статический класс `Runner` (`Runner.run`, `Runner.run_sync`). Цикл выполняет шаги: опрос модели -> вызов инструментов -> смена агента при handoff -> проверка `max_turns`.
- **Какие классы/API используются:** `agents.Runner`, `RunConfig`, `RunHooks`.
- **Что SDK предоставляет автоматически:** Полный цикл ReAct + Handoff без написания циклов `while`.
- **Что приходится писать разработчику:** Только вызов `await Runner.run(starting_agent, input)`.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/engine/executor.py` (`DialecticalEngine`).
- **Как он реализован:** Явный цикл `for iteration in range(1, max_iterations + 1)` с жестко разделенными фазами: `_phase_generate()` -> `_phase_collide()` -> `_phase_synthesize()` -> `_phase_validate()`. Включает детекторы холостого хода (idle loop) и принудительные толчки (nudges).
- **Какая архитектурная идея используется:** Принудительное соблюдение диалектического цикла. Агент физически не может выдать ответ пользователю, пока не завершит фазу Collision при наличии запрошенных инструментов.

### Различие
В OpenAI Agents SDK оркестрация адаптивная и не навязывает жестких этапов внутри одной итерации агента. В DialecticAI оркестрация является принудительным стейт-машиной со строгими фазами и активной борьбой с галлюцинациями и холостыми циклами.

---

## 8. Контекст (Context)

### OpenAI Agents SDK
- **Как реализован:** Контекст прогона передается через `context=` в `Runner.run` и автоматически внедряется в инструменты через аннотацию `RunContextWrapper[T]`.
- **Какие классы/API используются:** `RunContextWrapper`, параметр `context` в `Runner.run`.
- **Что SDK предоставляет автоматически:** Проброс контекста сквозь все вызовы инструментов и handoffs без загрязнения JSON Schema.
- **Что приходится писать разработчику:** Собственный dataclass/Pydantic-класс контекста сессии.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/core/schema.py` (`AgentInput`), `dialectic_ai/agent/base.py`.
- **Как он реализован:** Объект `AgentInput(user_message, session_id, metadata)` передается в `engine.run()`. Внутри агента контекст пополняется через историю сообщений и вызовы памяти.
- **Какая архитектурная идея используется:** Разделение входного стимула (`AgentInput`) и оперативного контекста доказательств (`EvidenceStore`).

### Различие
В OpenAI Agents SDK контекст — это единый произвольный объект состояния, внедряемый в рантайм через механизм зависимости (Dependency Injection) в инструменты. В DialecticAI контекст четко структурирован на метаданные запроса, список собранных `Evidence` и динамически сжимаемую память.

---

## 9. Состояние (State)

### OpenAI Agents SDK
- **Как реализован:** Состояние хранится в виде линейной истории сообщений диалога, объекта `RunState` и пользовательского контекста. Дополнительно поддерживаются сессии `Session` для персистентности между запусками.
- **Какие классы/API используются:** `Session`, `RunState`, `RunResult.to_state()`.
- **Что SDK предоставляет автоматически:** Сериализацию состояния диалога и возможность возобновления с места остановки.
- **Что приходится писать разработчику:** Настройку постоянного хранилища (например, Redis или файловое хранилище).

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/memory/` (`KnowledgeGraphMemory`, `SQLiteKnowledgeGraphMemory`, `SublationEngine`).
- **Как он реализован:** Граф знаний концептов (`concept -> status/data`) с сохранением в SQLite/JSON. При разрастании истории более 10 сообщений `SublationEngine` выполняет диалектическое «снятие» (Aufheben) — сжатие ранних сообщений с сохранением сути через отдельный вызов LLM.
- **Какая архитектурная идея используется:** Память как концептуальный граф знаний, отражающий развитие тезисов, а не просто сырой лог реплик.

### Различие
OpenAI Agents SDK полагается на канонический список сообщений чата (Chat History) и персистентные сессии. DialecticAI строит семантический граф фактов и применяет процедуру «снятия» (диалектической суммаризации) для контроля размера окна.

---

## 10. Трассировка (Tracing)

### OpenAI Agents SDK
- **Как реализован:** Полноценная встроенная модель распределенной трассировки OpenTelemetry-типа.
- **Какие классы/API используются:** `TracingProcessor`, `add_trace_processor`, `Span`, `AgentSpanData`, `FunctionSpanData`, `HandoffSpanData`, `GenerationSpanData`, `enable_verbose_stdout_logging`.
- **Что SDK предоставляет автоматически:** Автоматический старт/завершение спанов на каждый чих системы (запрос модели, вызов тула, смена агента, валидация гардрейлов) с фиксацией латентности, токенов и ошибок.
- **Что приходится писать разработчику:** Кастомный процессор только в случае экспорта в сторонние хранилища.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/core/logger.py` (`DevelopmentLogger`), `dialectic_ai/observability/tracer.py` (`TraceReader`), `dialectic_ai/observability/evaluator.py`.
- **Как он реализован:** Запись JSONL-событий в `trace.jsonl` по фазам диалектического цикла (`engine_start`, `generate`, `tool_call`, `collision`, `synthesis`, `validation`, `idle_loop`).
- **Какая архитектурная идея используется:** Оценка трассы не просто по таймингам, а по философской корректности мышления агента (выявление `rule5_violations`, пропусков синтеза или нестыковок слов и действий).

### Различие
OpenAI Agents SDK предоставляет индустриальный стандарт системного трейсинга (Spans/Traces с метаданными и метриками выполнения). DialecticAI ориентирован на проблемно-ориентированный аудит (соответствие логики агента методологии Rule 5 и выявление архитектурных противоречий).

---

## 11. Обработка ошибок (Error Handling)

### OpenAI Agents SDK
- **Как реализован:** Встроенный трехуровневый контур:
  1. Ошибки инструментов транслируются в текстовые ответы инструментов для модели.
  2. Сетевые ошибки LLM обрабатываются политикой `RetryPolicy` с автоматическим повтором.
  3. Ошибки прогона перехватываются через `error_handlers` в `Runner.run`.
- **Какие классы/API используются:** `RetryPolicy`, `RunErrorHandlers`, `UserError`.
- **Что SDK предоставляет автоматически:** Превращение исключений Python из функций-инструментов в сообщения об ошибках, доступные LLM для самоисправления без краша пайплайна.
- **Что приходится писать разработчику:** Специфичные обработчики фатальных сбоев.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/core/retry.py` (`retry_call`), `dialectic_ai/engine/repair.py` (`JsonRepairer`), `dialectic_ai/engine/executor.py`.
- **Как он реализован:**
  1. Общий экспоненциальный бэкофф с джиттером для провайдеров (`RetryableError`).
  2. `JsonRepairer`: одна контролируемая попытка исправить сломанный JSON модели повторным промптом с внедренной схемой.
  3. Контроль повторяющихся ошибок: предупреждение агенту при повторении идентичного падающего вызова тула.
  4. Защита от противоречия слова и дела: `leap_action_mismatch` принудительно возвращает агента на шаг назад, если он заявил о действии, но не вызвал инструмент.
- **Какая архитектурная идея используется:** Контролируемое падение (fail-fast) при структурной невозможности ремонта и активное побуждение модели к рефлексии над собственной ошибкой.

### Различие
OpenAI Agents SDK реализует стандартную прагматичную модель отказоустойчивости (мягкая передача ошибки обратно модели). DialecticAI включает активную валидацию намерений (проверка на зацикливание, пустые ответы, нестыковку заявленного `leap_type` и пустой корзины доказательств).

---

## 12. Структурированный вывод (Structured Output)

### OpenAI Agents SDK
- **Как реализован:** Параметр `output_type` в конструкторе `Agent`.
- **Какие классы/API используются:** `Agent(output_type=PydanticModel)`, `result.final_output`.
- **Что SDK предоставляет автоматически:** Принудительное включение Structured Outputs (JSON Schema mode) в API модели и валидацию ответа через Pydantic.
- **Что приходится писать разработчику:** Pydantic-модель целевой структуры данных.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/core/schema.py` (`AgentOutput`), `dialectic_ai/engine/parser.py`.
- **Как он реализован:** Модель обязана всегда возвращать структурированный JSON с фиксированным набором мета-полей (`hypothesis`, `decision`, `tool_calls`, `response`, `opposite_process`, `contradiction`, `leap`, `leap_type`). При сбое подключается `JsonRepairer`.
- **Какая архитектурная идея используется:** Структурированный вывод — это не опция для разработчика, а фундаментальная основа работы движка, позволяющая проверять ход мысли агента.

### Различие
В OpenAI Agents SDK структурированный вывод применяется гибко и по желанию к конечному результату агента. В DialecticAI структурированный формат является обязательным внутренним языком каждого витка рассуждений агента.

## 13. Запуск рабочего процесса (Workflow Execution)

### OpenAI Agents SDK
- **Как реализован:** Вызов асинхронного метода `Runner.run(starting_agent, input, ...)` или синхронного `Runner.run_sync(...)`.
- **Какие классы/API используются:** `Runner`.
- **Что SDK предоставляет автоматически:** Инициализацию сессии, запуск цикла обработки, вызов инструментов, диспетчеризацию handoffs, сборку итогового ответа.
- **Что приходится писать разработчику:** Одну строчку запуска с передачей параметров.

### Мой framework
- **Где находится аналогичный механизм:** `dialectic_ai/engine/executor.py` (`DialecticalEngine.run()`), `dialectic_ai/multi/triad.py` (`DialecticalTriad.run()`), CLI `dialectic run`.
- **Как он реализован:** Инстанцирование движка с передачей сконфигурированного агента и последующий вызов `await engine.run(AgentInput(...))`.
- **Какая архитектурная идея используется:** Разделение декларации агента (`DialecticalAgent`) и исполнительного механизма (`DialecticalEngine`), что позволяет менять движки (одиночный, триада, дебаты) для одного и того же агента.

### Различие
В OpenAI Agents SDK `Runner` статичен и универсален для всех конфигураций агентов (один агент или сеть с handoffs запускаются одинаково). В DialecticAI запуск мультиагентных систем требует специализированных композиционных классов (`DialecticalTriad`, `DialecticalDebateEngine`), так как они реализуют принципиально разные протоколы взаимодействия.

## 14. Расширение системы новыми агентами (Extensibility)

### OpenAI Agents SDK
- **Как реализован:** Создание нового экземпляра `Agent(...)` и добавление его в список `handoffs` существующих агентов.
- **Какие классы/API используются:** `Agent`, `handoff`.
- **Что SDK предоставляет автоматически:** Новые агенты моментально становятся доступны для перехода без правки ядра фреймворка или оркестратора.
- **Что приходится писать разработчику:** Определение нового агента и добавление ссылки на него в родительские агенты.

### Мой framework
- **Где находится аналогичный механизм:** Создание нового агента через `DialecticalAgent`, регистрация в `AgentRouter` или включение в состав роли в `DialecticalTriad` / `DialecticalDebateEngine`.
- **Как он реализован:** Создание агента с описанием его `goal`, подбором провайдера LLM и памяти, а также обязательным декларированием слоя и диалектических характеристик при создании вспомогательных классов через `@dialectical`.
- **Какая архитектурная идея используется:** Агент не является изолированным островом: создание агента сопровождается фиксацией его места в слоях архитектуры (Layer 1–4) и осмыслением его противоречий.

### Различие
В OpenAI Agents SDK расширение системы предельно простое и локальное (peer-to-peer связывание через списки handoffs). В DialecticAI расширение требует определения роли агента в диалектической композиции (кто является генератором-тезисом, кто критиком-антитезисом, кто арбитром-синтезом, либо регистрация правила в роутере).
