# Framework Benchmark Harness: DialecticAI vs. OpenAI Agents SDK

## 1. Цель Benchmark Harness
Предоставить строго нейтральный, изолированный измерительный стенд для сравнительного исследования двух принципиально разных агентных парадигм:
- **DialecticAI:** архитектурно-принудительный цикл (Rule 5, фазы generate → collide → synthesize → validate, класс Evidence, EvidenceStore, Action-Execution consistency).
- **OpenAI Agents SDK:** модель-центричный адаптивный цикл (Agent, Runner, handoffs, function_tool, TracingProcessor).

> **Ключевой принцип стенда:**  
> *Harness does not score frameworks. Harness records execution.*  
> (Измерительный стенд не выносит оценок и не определяет, кто «лучше». Он объективно фиксирует наблюдаемые факты исполнения).

## 2. Структура файлов стенда

```text
experiments/framework_benchmark/
├── __init__.py            # Пакетный маркер
├── benchmark_env.py       # Изолированное серверное хранилище наборов данных (Dataset A и B)
├── benchmark_case.py      # Сценарии оценки: Case O (Оппозиция), Case C (Противоречие), Case U (Провокация)
├── tools.py               # Чистое математическое ядро вычислений (без зависимостей от фреймворков)
├── events.py              # Нейтральная модель наблюдаемых событий (BenchmarkEvent) и логгер
├── run_dialectic.py       # Адаптер и раннер для DialecticAI (Single Agent и Triad)
├── run_openai_sdk.py      # Адаптер и раннер для OpenAI Agents SDK (Handoff Pipeline)
├── results/               # Каталог для структурированных JSON-логов прогонов
└── README.md              # Документация измерительного стенда
```

## 3. Разделение среды данных (Environment) и промпта LLM
В отличие от тривиальных тестов, где числа передаются прямо в системный промпт, данный стенд исключает утечку данных:
- Сырые массивы `[40, 45, 50, 55, 60]` и `[10, 10, 10, 20, 200]` хранятся в модуле `benchmark_env.py`.
- Модели видят исключительно абстрактные идентификаторы `'A'` и `'B'`.
- Для доступа к данным модель обязана совершить вызов инструмента `calculate_statistics("A")` или `compare_datasets("A", "B")`.
- Это позволяет абсолютно строго проверить:
  1. Вызывает ли система инструменты на самом деле.
  2. Выдумывает ли модель неподтверждённые свойства данных (например, бимодальность), если инструмент вернул только базовые сводные показатели.

## 4. Единая вычислительная база
Оба адаптера (`run_dialectic.py` и `run_openai_sdk.py`) вызывают **одни и те же функции** из `tools.py`:
- Никакой дублирующей арифметики;
- Никаких скрытых эвристик;
- Никаких готовых текстовых выводов в выводе инструментов.

## 5. Что считается фактом (Observed) против интерпретации (Inferred)

### Категория Observed (Фиксируется в логах Event Logger):
- Факт вызова инструмента с аргументами `{"dataset_id": "A"}`.
- Создание объекта `Evidence` с UUID `e4a1...` в `EvidenceStore`.
- Переход управления от `Planner_Agent` к `Analysis_Agent` через `handoff`.
- Вызов метода `_phase_validate` и проверка наличия ID улики в локальном реестре.
- Значение поля `leap_action_mismatch == True`.

### Категория Inferred (Оставляется для итогового аналитического отчёта):
- «DialecticAI обеспечивает более строгий контроль ссылочной целостности».
- «OpenAI Agents SDK даёт модели больше гибкости».
- «Разрыв между EvidenceStore Тезиса и Синтеза ослабляет формальные гарантии Триады».

## 6. Что НЕ является результатом benchmark до фактического запуска
До момента проведения серии запусков на Этапах 5–10:
- Наличие кода harness не доказывает работоспособность гипотез.
- Отсутствие синтаксических ошибок не означает идентичность семантического поведения.
- Любые сравнительные таблицы и выводы остаются заблокированными до получения эмпирических трейсов.
